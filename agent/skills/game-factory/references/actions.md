# Действия сервиса и сохранение состояния

Используй только доступные `game_factory_status` и `game_factory_control`. Личность автора, текущий запуск и допустимые корни исходников определяет хост. Не передавай собственные identity, runId, capability, tenant или полномочия в `args`. Не исправляй ошибки доступа прямой записью конфигурации/БД или вызовом внутреннего Python/Node-модуля.

## Общий запрос

Оба инструмента принимают `operationId`, `action`, необязательные `projectId`, `expectedRevision`, `args`. Для изменения существующего проекта нужны `projectId` и **актуальная `project.revision`** в `expectedRevision`; для `create` — выбранный новый `projectId` и `expectedRevision: 0`.

`project.revision` меняется при каждой успешной мутации. `brief.revision` — версия требований; это другое число. Не вычисляй новую ревизию самостоятельно: бери её из ответа или нового `inspect`.

ID проекта/задачи/ключа решения: 3–80 символов, шаблон `^[a-z][a-z0-9_-]{2,79}$`. `operationId`: 8–128 символов, буквы/цифры/`:_-`, первый символ — буква или цифра. Придумай его один раз для конкретного запроса и сохрани до подтверждённого результата.

После тайм-аута результат **неизвестен**: выполни чтение и при необходимости повтори **тот же полный запрос**, с тем же `operationId`, аргументами и исходным `expectedRevision`. Не создавай вторую задачу, импорт или платную генерацию из-за отсутствующего ответа. `operation_id_conflict` означает повторное использование ID с другим запросом; сначала восстанови, что произошло. При явном конфликте ревизии перечитай проект, учти поправки и сформируй отдельный новый запрос. Не меняй аргументы уже выполняющейся операции.

## Чтение

Все чтения используют `game_factory_status`; `expectedRevision` не требуется.

| `action` | `args` | Как использовать |
|---|---|---|
| `capabilities` | `{}` | Доступные backend, создание проектов, `publicationAccounts` с alias/площадкой и фактический режим `prepare_only`. |
| `list` | `{}` | Только доступные текущему автору проекты. |
| `context` | `{taskId?}` | Требует `projectId`. Текущий бриф, до пяти решений и до двух задач. |
| `peer_result` | `{jobId}` | Подтверждённый сохранённый результат peer: имена, размеры и хеши файлов. Требует projectId и прав; не приёмка качества. |
| `inspect` | `{section?, receiptId?, cursor?, limit?}` | Требует `projectId`. `section`: `overview`, `tasks`, `taskHistory`, `decisions`, `builds`, `operations`, `evidence`, `releases`, `assets`, `briefHistory`, `check`. Для check нужен receiptId из evidence; возвращается полный host receipt с хешем. Для страниц по умолчанию cursor=0, limit=5; максимум limit=10. |

Следуй `nextCursor`, если нужна полная история раздела. Даже внутри страницы `builds` список файлов может быть усечён: проверяй `fileListComplete`/`totalFiles`. Короткий ответ не доказывает отсутствие старого решения, задачи или ассета.

Пример чтения доступных возможностей:

```json
{"operationId":"read-capabilities-0001","action":"capabilities","args":{}}
```

## Бриф, решения, план и доступ

Все следующие действия — `game_factory_control` с общими полями запроса.

**Полный бриф** для `create.args.brief` или `brief.args`:

```json
{
  "goal":"Какой результат должна дать игра",
  "audience":"Для кого она",
  "firstSession":"Что игрок поймёт и сделает при первом запуске",
  "coreLoop":"Действие, обратная связь, цель и повтор",
  "artDirection":"Согласованный образ, стиль и ограничения",
  "acceptance":["Наблюдаемый критерий первого законченного фрагмента"],
  "devices":["desktop"],
  "platforms":["local"],
  "exclusions":[],
  "budget":{"currency":"USD","limitMicros":0},
  "publication":"prepare_only"
}
```

`devices`: `desktop`/`mobile`; `platforms`: `local`/`yandex`/`crazygames`/`roblox`. `limitMicros` — целое число миллионных долей USD; ноль не разрешает платные операции. Декларация лимита в брифе сама по себе не является разрешением провайдера на расход.

| `action` | Точные `args` | Существенное поведение |
|---|---|---|
| `create` | `{title, engine, brief, origin?}` | `engine`: `canvas`, `phaser`, `threejs`, `roblox`, `other`. `origin`: `{projectId?, note}`. Создаёт приватный проект текущего автора. |
| `brief` | Полный бриф выше | Заменяет текущие требования; незавершённые задачи становятся устаревшими, действующий редактор требует сверки. |
| `decision` | `{key, value, state}` | `state`: `proposed` или `accepted`. Принятие или замена принятого решения обновляет версию требований. Не повышай предложение ассистента до принятого решения. |
| `forget_decision` | `{key}` | Удаляет текст версий этого решения из проектной памяти. Не возвращай его через старые записи/резюме; если пользователь явно вводит решение заново, сохраняй новое основание. |
| `plan` | `{tasks:[{id,stage,title,acceptance,dependencies,humanReviewRequired?}]}` | 1–50 задач, критерии непустые. Зависимости должны находиться раньше в том же массиве; ID задачи нельзя повторно использовать из истории. Старый план архивируется. Нельзя перепланировать при занятой блокировке. Для оценки первого игрового фрагмента поставь humanReviewRequired=true; для обычной технической подзадачи не добавляй лишний барьер. |
| `share` | `{alias,role}` | Только owner проекта; роль `editor`, `reviewer`, `reader` либо `null` для отзыва. Alias должен уже существовать в конфигурации; не выводи его из личных ID. |
| `pause` / `cancel` / `resume` | `{}` | Отмена/возобновление — owner; пауза доступна editor. `resume` только для paused после сверки старого редактора. Реестр сам по себе не останавливает внешнего исполнителя. |

Стадии задач: `brief`, `playable`, `art`, `content`, `qa`, `package`, `release`, `learn`. Не превращай их в обязательные восемь отдельных задач для маленькой правки.

## Один редактор и сохранение работы

| `action` | Точные `args` | Ограничение |
|---|---|---|
| `claim` | `{taskId,backend,baseBuildId?,ttlSeconds?}` | Backend только из capabilities; TTL 60–3600 секунд, по умолчанию 600. Возвращает `claim.token` и отдельный `workDirectory`; с baseBuildId хост проверяет исходный manifest и подготавливает `sourceDirectory`. Зависимости должны быть приняты, задача — текущей версии. |
| `renew_claim` | `{token}` | Продлевает текущую блокировку того же запуска; не присваивает чужую или устаревшую. |
| `checkpoint` | `{token,summary,state,buildId?}` | `state`: `working`, `submitted`, `blocked`. Для submitted нужен текущий build, кроме стадий brief/learn. Submission не означает quality acceptance. |
| `release_claim` | `{token}` | Только после завершения своей записи и сверки связанных внешних операций. Не освобождает работающий peer/desktop по догадке. |
| `reconcile` | `{}` | Хост должен подтвердить завершение старого запуска и отсутствие неразрешённых внешних операций. Истечение TTL или сон машины этого не доказывают. |

Работай в возвращённом `workDirectory` средствами разрешённого исполнителя. Если исходники уже есть, выполни `source_import` **до claim**, затем передай его build ID как `baseBuildId` и редактируй полученный `sourceDirectory`. Для продолжения можно выбрать другой проверенный build того же проекта. Оригинал и сохранённые imports/builds не редактируй. Блокировка реестра не делает произвольную запись через shell безопасной: останови редактора, когда требования, права или состояние задачи изменились.

При `newer_user_input_pending` сначала обработай новое сообщение. При `writer_lease_mismatch`, `lease_reconciliation_required`, `previous_execution_not_confirmed_finished`, `external_execution_unresolved` не удаляй блокировку вручную и не запускай второго редактора. Сохрани результат старого исполнителя отдельно, проверь фактическое завершение и продолжи после штатной сверки.

## Исходники, сборки и доказательства

| `action` | Точные `args` | Что действительно подтверждает |
|---|---|---|
| `source_import` | `{sourceRoot,entrypoint,note,version?}` | Без активного claim. SourceRoot — выбранное дерево исходников в разрешённых хостом корнях; entrypoint относительный. Создаёт отдельную приватную копию и manifest. По умолчанию version=`source-import`. |
| `build_capture` | `{token,sourceRoot,entrypoint,version}` | SourceRoot только внутри workDirectory действующего claim. Хост сохраняет отдельный snapshot сборки с файлами/размерами/хешами, а не указатель на меняющийся рабочий код. |
| `evidence_record` | `{buildId,kind,criterion,result}` | `kind`: `technical`, `browser`, `device`, `human`, `platform`; `result`: `pass`, `fail`, `unknown`. Запись всегда `reported`: она не превращается в host-проверку или согласие человека. |
| `verify_build` | `{buildId}` | Хост проверяет HTML5 startup на текущем manifest и сохраняет receipt. Результат `passed` означает только startup smoke; Roblox требует Studio-проверки. |
| `human_feedback` | `{buildId,messageId,quote,result}` | Quote — дословный фрагмент текущего сообщения пользователя о показанной сборке. Хост проверяет источник, но трактовка pass/fail/unknown остаётся агентской. Это не разрешение публикации. |
| `task_review` | `{taskId,decision,note,evidenceIds}` | Decision: `accepted` или `changes_requested`. Задача должна быть submitted, её редактор и внешние операции — завершены и сверены. Принятие требует проверенных доказательств для её build; при humanReviewRequired — подтверждённого пользовательского отзыва. Это решение координатора, не доказательство полного прохождения. |
| `asset_register` | `{relativePath,kind,provenance,rights,state,provider?,externalId?,costMicros?}` | Path относительно workspace. Kind: `image`, `audio`, `video`, `font`, `model`, `other`; state: `candidate`, `accepted`, `rejected`. Хост проверяет файл, но указанная стоимость требует квитанции провайдера. |
| `operation_link` | `{kind,externalId,taskId?}` | Kind: `peer`, `image`, `legacy`, `desktop`, `delivery`, `asset`. Только ссылка со статусом reported; не запуск, оплата, завершение или доставка. |
| `image_job_link` | `{jobId,taskId?}` | Наблюдает существующее задание текущего автора в image pipeline и сохраняет проектную ссылку; не начинает генерацию. |
| `image_asset_import` | `{jobId,artifactId,rights}` | Импортирует ровно выбранный подтверждённый файл своего image job как candidate. Не раскрывает соседние картинки и личные запросы; стоимость неизвестна без квитанции, права остаются заявленными. |
| `asset_review` | `{assetId,state,note}` | state accepted/rejected, повторная сверка хеша. Оценка координатора; не выдумывай человеческое согласие или лицензию. |

Рабочий цикл: `claim` → правка рабочей копии → `build_capture` → `verify_build` и нужные проверки/отзыв → `checkpoint` со state=submitted и buildId → завершение внешнего исполнения/`release_claim` → `task_review`. На каждом изменении используй новую актуальную project.revision. После фиксации сборки не меняй её snapshot; следующая правка рабочей копии получает новый build. Не принимай задачу вопреки известным ошибкам или `unknown` по её критериям; не обходи требование отзыва через `evidence_record`. Если установленная версия хоста не предоставляет действие, не подменяй его внутренними модулями или самостоятельной записью `trust: host_verified`.

## Задание второму исполнителю

Сначала `claim` с `backend: "peer"`. `peer_dispatch.args`:

```json
{
  "token":"полученный-токен",
  "expectedOutputs":[{"name":"result.zip","kind":"code"},{"name":"report.txt","kind":"text"}],
  "acceptance":[{"id":"has-report","kind":"file_present","description":"Отчёт о фактически выполненных проверках","outputName":"report.txt"}],
  "timeoutSeconds":1200,
  "allowBattery":false
}
```

Можно добавить `goal` и `inputBuildId`. Для правки существующей игры укажи исходный build: хост передаст проверенный `source.zip`; локальный путь Mac Mini не является передачей исходников на другой компьютер. Outputs имеют kind `text`, `document`, `photo`, `code`; имена без каталогов, точек в начале, переводов строки и дублей.

Критерии acceptance: `{id,description,kind,outputName?,expected?,scenario?}`. Kind — `manual`, `text_contains`, `file_present`, `file_contains`, `file_sha256`, `json_parse`, `artifact`. Для файловых проверок нужен объявленный outputName; для contains — expected; для file_sha256 — точный SHA-256. Не выдумывай содержимое `scenario`: используй только доступную схему проверяющего инструмента либо явный ручной критерий. Ограничения: 1–20 outputs, 1–30 criteria, timeout 60–7200 секунд.

Сохранённый `peerJobId` и `remoteAccepted:false` означают локально зарезервированную отправку. Для сверки используй `peer_refresh` с `args: {operationId: ...}`, где внутренний operationId — ID **проектной peer-операции из ответа**, а внешний operationId запроса — новый ID этой сверки. Не создавай вторую peer-задачу, пока первая linked/running/unknown. Доставка, приём результата и приёмка качества учитываются отдельно. GUI, публикация, сообщения другим людям и платные сервисы этим делегированием не разрешаются.

После подтверждённого окончания peer используй `peer_result` для списка файлов и `peer_import` с `{jobId, artifactName?, entrypoint, version}` для новой неизменяемой сборки. Для ZIP явно укажи artifactName, например result.zip; без него импортируется весь допустимый плоский набор файлов этого задания. Хост проверяет происхождение и хеши, безопасно распаковывает архив и отклоняет устаревшие требования. Выполни `verify_build` и согласованные игровые проверки. Успех исполнителя не заменяет task_review.

Истечение срока транспортного поручения не удаляет уже подтверждённый результат. Его можно импортировать позднее, если права, бриф и требования задачи по-прежнему действуют и нет конфликтующих финальных ответов. Это не возобновляет исполнение истёкшего поручения. При конфликте результатов не выбирай удобную версию автоматически: останови приёмку и сверяй сохранённые свидетельства.

`legacy` — ограниченный генератор Canvas/Phaser-эскиза. Сначала claim backend=legacy, затем `legacy_dispatch` `{token,timeoutSeconds?}` (120–1800 секунд, по умолчанию1200). Сохрани legacyJobId. `legacy_refresh` `{jobId}` читает состояние, `legacy_cancel` `{jobId}` сохраняет отмену; stopped=false требует сверки. `legacy_import` `{jobId,version}` переносит завершённый текущий результат в новый build. Музыка отключена, платные API и публикация не запускаются. Старую очередь не возобновляй автоматически. После поправки можно сверить/отменить прежнее задание, но нельзя принять его как выполнение нового брифа.

Хост периодически сверяет уже отправленные legacy-задания и сообщает подтверждённый исход в исходный разрешённый чат, даже когда текущий разговор закончился. Это короткое уведомление о кандидате, ошибке или подтверждённой отмене; оно не принимает игру и не доставляет её архив. При неизвестном результате отправки хост сохраняет `unknown` и не повторяет сообщение вслепую. Для исторического задания без подтверждённого адресата автоматическая отправка недоступна; перенаправления в чужой или основной чат нет.

Desktop backend недоступен, пока не подключён проверенный адаптер. Наличие приложения и запись в private allowlist не являются доказательством готовности. `codex_desktop` сохраняет ограничение основного владельца даже в общем проекте; не обходи его через shell или другой чат.

## Подготовка релиза

`release_prepare.args`: `{buildId, platform, mode, accountAlias, sourceOfFirstPlayers, reviewAt}`. Mode: `preview`, `basic`, `full`; reviewAt — ISO datetime с timezone. Нужны build текущего брифа, площадка из брифа и настроенный для автора accountAlias из `capabilities.publicationAccounts`. Если нужного аккаунта нет, не угадывай alias и не ищи ключи в чужом аккаунте.

Результат `prepared` и `publicationAuthorized:false` — подготовка, не публикация. `release_observe.args`: `{releaseId,state,receipt}`, где state — `reported_submitted`, `reported_live` или `rejected`; это reported-наблюдение, не подтверждённая хостом отправка. Само действие не загружает игру и не даёт разрешения пользоваться внешним аккаунтом.

`release_package` `{releaseId}` создаёт настоящий повторяемый game.zip из точного manifest сборки. Хост проверяет базовые ограничения профиля и не перезаписывает изменённый архив. `releaseReady:false` сохраняется намеренно: пакет сам по себе не доказывает SDK, полное прохождение, промоматериалы или приёмку кабинетом. Передавай точный ZIP через существующий механизм доставки, фиксируй квитанцию отдельно; путь файла не означает, что человек его получил.
