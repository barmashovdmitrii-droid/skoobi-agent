# Roblox: отдельный локальный сценарий

Это ветка Luau/Rojo/Roblox Studio, а не экспорт HTML5. Поддержка инструментов не означает готовности мира к выпуску. Не возобновляй остановленный опубликованный проект автоматически.

## Подготовка и локальная сборка

1. Сверь исходник, незакоммиченные изменения, работающего редактора и источник правды: Rojo-генератор не импортирует ручные правки Studio. Сними manifest исходника и работай в новой приватной копии. В публичный модуль не входят аккаунты, place/universe/product/pass IDs, игровые ассеты и личные документы.
2. Раздели исходный проект, чистые тестовые fixtures и локальную конфигурацию Studio. Для проверки без внешних эффектов нужны `RELEASE=false`, `PERSISTENCE_ENABLED=false`, `ALLOW_STUDIO_PERSISTENCE=false`, `ANALYTICS_ENABLED=false`, universe IDs и все товарные IDs равны нулю. Каталог чистых тестов использует синтетические значения; его нельзя подключать к Studio вместо нулевой конфигурации.
3. Проверь знакомые серверные модули чистыми Luau-тестами: поддельные команды/награды, порядок действий, расстояния/тайминги, независимость игроков, ограничение частоты; миграции старых профилей и отказ от будущей схемы; lease-конфликты, сбои и повторы записи. Не запускай непроверенные project scripts просто потому, что они названы `check`.
4. Host-команда `ops/game-factory/roblox-local-build.py` принимает явную локальную копию. Она запускает только установленный Rojo, создаёт отдельный pinned source и XML place, сохраняет SHA256 исходников и результата. Это обслуживающая host-команда, **не новый action `game_factory_control`** и не обход отсутствующих прав/возможностей модели.

```sh
python3 ops/game-factory/roblox-local-build.py \
  --source-root /absolute/private/project-copy \
  --project default.project.json \
  --local-config src/shared/Config.luau \
  --output-parent /absolute/private/qa-output
```

Оба каталога должны существовать, быть каноническими; output-parent приватный и принадлежит текущему пользователю. Project JSON должен лежать в корне копии, `$path` — относительные, внутри неё; поддержаны Luau и JSON/CSV данные. Symlink/hardlink, выход за корень, неизвестные типы ассетов и превышение лимитов отклоняются. Скрипт не запускает Studio, Lua или код проекта; статические флаги не доказывают безопасность произвольного игрового кода.

## Studio и два клиента

Открой **собранную локальную копию**. Используй Studio `Test → Server & Clients`, два клиента. Сначала подтверди, что локальная конфигурация осталась отключённой от облака/аналитики/товаров. Не меняй Studio API access, аккаунт, permissions, security settings или публикацию ради теста.

Запиши фактический запуск сервера и двух независимых клиентов, ошибочные Remote-вызовы и отсутствие чужих наград/состояния. Пройди хотя бы один цикл обычным вводом. Автоматический teleport/walkthrough полезен для проверки правил, но не заменяет обычный ввод и отзыв человека. Сохраняй скриншоты/Output, хеш place и отдельные результаты для каждого клиента.

Если Studio не запускается, нет доступа к интерфейсу или нужен вход, отметь точный наблюдённый барьер. Установленная программа, живой PID, сборка Rojo и старый отчёт не подтверждают текущий запуск двух клиентов. Не переименовывай `built_only` в `studio_pass`.

## Сохранения и покупки

Чистые тесты с fake DataStore подтверждают логику в симуляции; настоящая запись, выход/возврат и работа двух серверов требуют отдельно разрешённого тестового мира и отдельного хранилища. Успех локального Play не означает облачное сохранение.

Для `ProcessReceipt` проверяй повтор до и после сбоя записи, параллельную доставку, повтор после reload и после большого числа следующих чеков. История только последних N покупок не обеспечивает неограниченную однократную выдачу: вытесненный незавершённый чек может снова начислить награду. До включения реальных товаров нужен проверенный durable механизм дедупликации, а не только успешный тест двух соседних повторов. Реальная покупка не входит в этот локальный сценарий.

Статусы фиксируются отдельно: `build passed`, `pure rules passed`, `Studio two clients passed/unverified`, `cloud save unverified`, `purchase simulation passed/limitations`, `human feedback`, `publication not requested`. QA-скрипты не попадают в релизную сборку.

Официальные источники, сверены 2026-11-04: [Studio testing modes](https://create.roblox.com/docs/studio/testing-modes), [player data and purchasing](https://create.roblox.com/docs/cloud-services/data-stores/player-data-purchasing), [DataStore best practices](https://create.roblox.com/docs/cloud-services/data-stores/best-practices), [place publishing](https://create.roblox.com/docs/cloud/guides/usage-place-publishing). Перед фактической публикацией их сверяют заново.

## Ограниченный guard повторов

`ops/game-factory/roblox/ReceiptLedger.luau` — переиспользуемый чистый серверный helper. `reserve(receipts, purchaseId, capacity)` возвращает `new`, `duplicate`, `capacity` или `invalid`; добавляет ID только для `new`, ничего не удаляет. Проверки: `luau-analyze ops/game-factory/roblox/ReceiptLedger.luau` и `luau ops/game-factory/roblox/receipt-ledger.test.luau`.

`new` и начисление выполняются без yield, после чего ID и награда сохраняются одной атомарной операцией профиля; `duplicate` не начисляет заново, но ожидает успешного сохранения. `capacity/invalid` означают отказ до начисления и явную причину для разработчика. Нельзя сбрасывать список, увеличивать ёмкость без проверки миграции или отвечать `PurchaseGranted` при неуспешной записи. Это ограниченный baseline для отключённых платежей, а не законченная платёжная система.
