# Установка игрового завода

Это операторская инструкция для существующего экземпляра Скуби. Сам навык находится в `agent/skills/game-factory`; игровые проекты, настройки участников, аккаунты, результаты и журналы хранятся отдельно от исходников.

## Проверка перед включением

Соберите и проверьте код в отдельном checkout. Не запускайте установку зависимостей, сборку или тесты из рабочей папки действующего сервиса. Сохраните точные ревизии и незакоммиченные изменения; подготовьте резервные копии исполняемого кода, настроек, LaunchAgent и согласованный SQLite backup. Обновление не должно заменять `data`, `store`, `groups`, `.env`, личные runtime homes или игровые исходники.

Конфигурация читается из `SKOOBI_GAME_FACTORY_CONFIG` либо `data/game-factory/config.json` экземпляра. Файл должен быть обычным, принадлежать пользователю сервиса, иметь права `0600` и единственную жёсткую ссылку. Приватные каталоги реестра и рабочих копий создаются с правами `0700`. Используйте канонические абсолютные пути без символических ссылок. Размещайте БД вне каталогов, разрешённых исполнителям для изменения и импорта.

Обязательные поля версии 1:

| Поле | Значение |
|---|---|
| `version` | `1` |
| `enabled` | Сначала `false`; включить после проверки конфигурации и работающего кода |
| `primaryOwnerIdentityId` | Проверенная host identity основного владельца |
| `actors` | Для каждого участника: `identityId`, `tenantId`, уникальный `alias`, `canCreate`, `backends`, `sourceRoots` |
| `workspaceRoot` | Отдельный существующий приватный каталог проектных рабочих копий |
| `databasePath` | Отдельный путь SQLite реестра |

Identity и tenant берутся из доверенного реестра хоста. Не назначайте их по словам модели. `sourceRoots` — узкие каталоги разрешённых игр; домашняя папка, все проекты сразу, каталог переписок и каталог настроек здесь не подходят. Разрешение участника в конфигурации не даёт доступа к чужим проектам: владелец отдельно назначает роль через `share`.

Дополнительные секции:

- `accounts`: только локальные alias площадок и разрешённые `actorAliases`. Это не ключи и не разрешение публикации. Режим остаётся `prepare_only`.
- `peer`: проверенный `coordinatorConfigPath`, `networkId`, `model` и `reasoningEffort` существующего peer-механизма. Обновите совместимый worker отдельно и проверьте фактический путь туда и обратно перед заявлением о готовности.
- `legacy`: `configurationPath` приватного адаптера старого генератора. В его конфигурации версии 1 задаются `pythonExecutable`, `factoryScript` и отдельный `stateDirectory`. Не подключайте историческую очередь для автоматического повторного запуска.
- `audio`: `configurationPath` приватного адаптера APIFrame/Suno. По умолчанию отсутствует; включение и разрешения на расходы описаны в [audio.md](audio.md). Ни наличие ключа, ни бюджет брифа не разрешают платный запрос.

Не включайте backend только потому, что приложение установлено. `capabilities` различает доступную текущую сессию, настроенный backend, которому ещё нужна проверка worker, и отсутствующий адаптер. Desktop-интеграции не появляются автоматически.

## Старый генератор

Обновляйте весь проверенный комплект Python, включая `managed_runtime.py`, вместе с управляемой конфигурацией worker. Нужны `GAME_FACTORY_CODEX_BIN`, `GAME_FACTORY_CODEX_HOME`, `GAME_FACTORY_CODEX_MODEL`, `GAME_FACTORY_CODEX_EFFORT` и явно назначенный доверенный источник `GAME_FACTORY_CODEX_AUTH_SOURCE`. Отдельный runtime parent не должен содержать личные сессии, настройки, навыки или MCP. Адаптер создаёт временный home на попытку и удаляет его после наблюдаемого завершения процесса.

Перед переключением проверьте активные jobs; не прерывайте их перезапуском службы. Исторические задания оставьте в архиве. Не запускайте два worker над одной очередью. Музыка и другие платные провайдеры не входят в проверку готовности и по умолчанию выключены.

## Проверка после установки и откат

Проверьте фактическую ревизию работающего процесса, доступность навыка и двух инструментов `game_factory_status` / `game_factory_control`. Чтение `capabilities` и `list` не должно создавать БД или запускать генерацию. Первый разрешённый цикл выполняется в отдельной проектной копии: создать бриф, получить claim, подготовить игру, зафиксировать сборку, проверить её и сформировать пакет. Проверяйте также отказ чужому участнику, новую поправку во время работы и повтор запроса с тем же `operationId`.

Фоновые legacy-уведомления содержат только подтверждённый исход существующего задания. Их `router_ack` подтверждает возврат используемого отправителя, а не прочтение человеком или Telegram message ID. Состояние `unknown` после обрыва не отправляется повторно автоматически. В уведомлениях нет перенаправления на владельца по умолчанию.

При откате сначала отключите новые заводские операции и дождитесь либо подтвердите остановку текущих исполнителей. Верните точный предыдущий код и настройки, сохранив новые реестры, provider IDs, результаты и квитанции для сверки. Не восстанавливайте старую очередь поверх уже принятых или оплаченных заданий. Перезапуск выполняйте существующим штатным механизмом экземпляра.

## Roblox

`roblox-local-build.py` — отдельная локальная ветка сборки, описанная в `agent/skills/game-factory/references/roblox.md`. Её квитанция не является HTML5 build или доказательством проверки в Studio. Для проверки сервера и двух игроков нужен фактический запуск Studio на безопасной копии. Реальные покупки, облачные сохранения и публикация не включаются сборщиком.
